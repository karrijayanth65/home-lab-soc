# Windows Service Creation Detection — Event ID 7045

## 1. Investigation Overview

This investigation demonstrates how Windows Service Creation activity can be detected and investigated using Windows Event ID 7045 and Wazuh.

The test was performed in a controlled Windows 10 virtual machine environment. A harmless test service named `SOC-Lab-7045-Test` was deliberately created so that the resulting Windows telemetry could be observed and followed through the Wazuh pipeline.

The investigation follows this path:

```text
Controlled service creation
        ↓
Windows System Event Log
        ↓
Event ID 7045
        ↓
Wazuh Agent
        ↓
Wazuh Manager
        ↓
Wazuh detection rule 61138
        ↓
Investigation and validation
        ↓
Controlled cleanup
````

The purpose of the exercise was not to simulate a real attack, but to understand how a SOC analyst can identify and investigate Windows service installation activity.

---

## 2. Why Event ID 7045 Matters

Windows Event ID `7045` is generated when a service is installed in the system.

Service installation is important from a security monitoring perspective because Windows services can be used legitimately by software, administrators, operating-system components, security tools, and virtualization software.

However, service creation can also be abused by attackers to establish persistence or execute code.

Therefore, an Event ID 7045 alert should be treated as an **investigation starting point**, not automatically as proof of malicious activity.

A SOC analyst should examine details such as:

* Service name
* Service executable or image path
* Service type
* Service start type
* Service account
* Creation time
* Host involved
* Surrounding activity
* Whether the service is expected in the environment

---

## 3. Investigation Objective

The objectives of this controlled test were:

1. Confirm that Windows generates Event ID 7045 when a service is created.
2. Identify the important fields contained in the Windows event.
3. Confirm that Wazuh receives and decodes the event.
4. Identify the Wazuh rule associated with the service-creation event.
5. Examine the MITRE ATT&CK mapping provided by the Wazuh rule.
6. Validate the test service locally.
7. Remove the controlled test artifact after evidence collection.

# 5. Controlled Service Creation

A controlled test service was created specifically for this investigation.

The following service was created:

```text
Service Name:       SOC-Lab-7045-Test
Image Path:         C:\Windows\System32\notepad.exe
Service Type:       user mode service
Start Type:         demand start
Service Account:    LocalSystem
```

The service was intentionally created but **not started**.

The command used was:

```powershell
sc.exe create SOC-Lab-7045-Test binPath= "C:\Windows\System32\notepad.exe" start= demand
```

The purpose was to generate predictable Windows telemetry without executing the configured service binary.

# 7. Wazuh Ingestion

The next objective was to determine whether the Windows event reached Wazuh.

The Wazuh Threat Hunting Events view was filtered using:

```text
agent.id:001 AND data.win.system.eventID:7045
```

### Screenshot — Wazuh Event 7045 ingestion

![Wazuh Event 7045 ingestion](../screenshots/Case%205/Wazuh_01_7045_ingested.png)

Wazuh returned the controlled event from the `Windows-10-Lab` agent.

The Wazuh event was associated with:

```text
Rule ID:     61138
Rule Level:  5
Description: New Windows Service Created
```

This proves that the Windows Event 7045 generated on the endpoint was successfully collected and processed by Wazuh.

The telemetry path is therefore:

```text
Windows 10
    ↓
Event ID 7045
    ↓
Wazuh Agent
    ↓
Wazuh Manager
    ↓
Rule 61138
```

![Wazuh decoded Event 7045 fields](../screenshots/Case%205/Wazuh_02_7045_details.png)

Important decoded fields included:

| Field        | Value                             |
| ------------ | --------------------------------- |
| Agent ID     | `001`                             |
| Agent Name   | `Windows-10-Lab`                  |
| Service Name | `SOC-Lab-7045-Test`               |
| Image Path   | `C:\Windows\System32\notepad.exe` |
| Service Type | `user mode service`               |
| Start Type   | `demand start`                    |
| Account      | `LocalSystem`                     |
| Event ID     | `7045`                            |
| Channel      | `System`                          |

This is important because a SIEM is most useful when raw operating-system events are converted into searchable fields.

Instead of having to read the entire Windows message manually, an analyst can search individual fields such as the service name or image path.

# 10. Wazuh Detection Rule and MITRE ATT&CK Mapping

The Wazuh event was associated with rule `61138`.

### Screenshot — Wazuh Rule 61138

![Wazuh Rule 61138](../screenshots/Case%205/Wazuh_04_rule_61138.png)

The rule information shown in Wazuh was:

```text
Rule ID:       61138
Rule Level:    5
Description:   New Windows Service Created
```

The event was mapped by Wazuh to:

```text
MITRE ATT&CK ID: T1543.003
Technique:       Windows Service
Tactic:          Persistence, Privilege Escalation
```

The MITRE mapping helps an analyst understand the security behavior represented by the alert.

It does **not** mean that this controlled test was malicious.

In this lab, the behavior was intentionally generated so that the detection could be studied.

# 14. SOC Analyst Takeaway

A Windows service-creation alert should not immediately be classified as malicious.

A practical investigation should ask:

1. **What service was created?**
2. **What executable does it point to?**
3. **Where is that executable located?**
4. **Which account will the service run as?**
5. **What is the start type?**
6. **Was the service expected on this endpoint?**
7. **What happened around the service creation time?**
8. **Is there related process, PowerShell, authentication, or network activity?**

In this controlled lab, the answers were known because the service was deliberately created.

In a real SOC investigation, these same questions help determine whether a 7045 alert represents normal administrative/software activity or potentially suspicious persistence.

# 15. Conclusion

This investigation demonstrated how Windows Service Creation activity can be traced from the endpoint to the SIEM.

The controlled service creation generated Windows Event ID 7045, Wazuh successfully ingested and decoded the event, and Wazuh rule `61138` identified the behavior as a new Windows service.

The investigation also demonstrated why context matters: the Windows host already contained legitimate 7045 events generated by software such as Wazuh, Microsoft components, and VirtualBox.

The final controlled service was removed after evidence collection.

The complete investigation chain was:
